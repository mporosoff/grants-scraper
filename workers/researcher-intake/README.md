# Funding Finder researcher intake

This Worker is the single private queue for researcher corrections and broader-pool nominations submitted from the public Configure Faculty Interests page or Team Match. Public requests are schema-bounded, origin-restricted, rate-limited, idempotent, and stored in the existing private Funding Finder D1 database. Contact email and submitter notes never enter public projections.

The admin console also includes **Manage researcher catalog**. Search for a person, choose **Retired**, **Left institution**, or **Inactive**, add a note, and select **Review removal**. The request enters the existing review queue; **Start review**, then **Approve and start publication**, applies the change through the same validated registry publication. Retirement maps to registry status `inactive`; departure maps to `departed`. Both hide the profile and disable automatic proposals.

Removal changes only `status`, `pool_visibility`, and `auto_proposable`. Stable researcher IDs, aliases, evidence, claim revisions, and historical references remain intact. Current matching projections exclude removed people, directory search omits them, and affected proposed teams are withheld pending regeneration. A profile correction alone cannot reactivate a removed researcher: that requires an explicit administrator policy change. The new D1 migration `0004_catalog_removals.sql` records the removal category and prevents simultaneous active removal requests for one researcher. Deployment applies it before updating the Worker; public submissions cannot set this administrator-only field. Rebasing preserves removal intent and refreshes the displayed current profile without copying public evidence projections back into the canonical registry.

Cloudflare Access must protect `/admin*`. The Worker independently verifies the Access JWT signature, issuer, audience, expiry, and allowlisted email, so a missing or incomplete Access configuration fails closed. Approval accepts only structured researcher fields, verifies the live registry generation, records each state change and its audit transition atomically, and dispatches only a submission ID, approved revision, and expected generation to the registry publication workflow.

If another publication advances the registry first, an administrator must use **Rebase onto current registry**. That audited action updates the request's base generation, returns it to `under_review`, clears the old approved payload and publication failure metadata, and requires a fresh approval before it can be dispatched again. If approval succeeds but the transition to publication fails transiently, **Retry publication** resumes the still-approved record; if the registry advanced in the meantime, that approved record can be rebased first. Before enabling auto-merge, the publication workflow records the exact pull request and target registry generation. If Pages verification later times out, **Reconcile publication** verifies the pull-request outcome and exact live generation before marking the record published, or marks a confirmed unmerged closure as failed so it can be retried. Pre-merge failures retry their queue callback and fail visibly if the private state cannot be updated.

Required secret bindings are `ADMIN_EMAILS`, `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `RECEIPT_TOKEN_SECRET`, `REGISTRY_WORKFLOW_TOKEN`, `GITHUB_DISPATCH_TOKEN`, `RESEND_API_KEY`, `ADMIN_NOTIFICATION_EMAIL`, and `NOTIFICATION_FROM`. `ACCESS_TEAM_DOMAIN` is the full `https://<team>.cloudflareaccess.com` domain and `ACCESS_AUD` is the protected application's audience tag. The deployment stops before touching D1 when any required credential or notification binding is missing. Rejected records default to a 90-day retention window. Private contact fields expire 90 days after their initial collection regardless of later workflow activity, and published records clear them immediately.

`GITHUB_DISPATCH_TOKEN` must be scoped to repository dispatch for this repository and must be distinct from the `RESEARCHER_GITHUB_PUBLICATION_TOKEN` used only inside the publication workflow for branch and pull-request writes. The deployment's bulk secret update also deletes the legacy `GITHUB_PUBLICATION_TOKEN` Worker binding. `REGISTRY_WORKFLOW_TOKEN` must match the GitHub Actions secret of the same purpose. None of these credentials is returned by a browser route.
