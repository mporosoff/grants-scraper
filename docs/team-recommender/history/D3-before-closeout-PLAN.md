## 3. Ingredients: source scope, scientific aspects, and public profiles

### 3.1 Admit a coherent scope, not a broad parent

A scope is a specific current call, a publication-eligible child, or an existing source-declared branch. Broad parents keep the unchanged chooser. Do not construct a synthetic team from unrelated siblings. Missing or ambiguous scientific structure produces an explicit unprepared/unsupported outcome; an expired scope is a different outcome.

Separate two checks: (a) the source supports a coherent research purpose; (b) the directory supports a reasonable group. An empty candidate pool must not turn genuine research into a nonresearch call. A sparse source must not be supplemented with an invented experiment.

Reuse authoritative source structure before asking a model to interpret it. One bounded extraction operation may prepare a materially changed scope, with existing bounded transport correction, if separately budgeted. Do not call an LLM for every person, group, or click. Repeated model outputs on unchanged sources must not be sought until a favorable interpretation appears.

### 3.2 Aspect record and weights

Start with a small source-proportionate aspect set, typically 3–6, but do not force a count. The existing renderer can represent a bounded number of roles; inspect its actual limit. One scientific aspect is permissible as input even if no complementary two-person group results. More source requirements than the supported display limit require lossless source-backed grouping or an honest limitation—not dropped requirements.

Each aspect records `aspect_id`, coherent `approach_id`, source `group_id`, concise description, original source span/locator/hash, central/supporting/optional kind, an operation descriptor only when supported, applicable context/object, and explicit conditions or exclusions. Record whether it is a source requirement or a planning contribution; do not invent sponsor mandates.

Keep conjunctions, alternatives, and conditional contributions distinct. The initial engine does not enumerate arbitrary combinations of source branches. It evaluates each prepared coherent approach independently. If the unchanged interface cannot truthfully present multiple approaches, support the source-declared selected child/branch or defer the ambiguous parent; never mix approaches in one group.

Within an approach, nonnegative weights sum to one. Group weights prevent repeated phrasing or splitting one aspect into synonyms from increasing its scientific importance. Children of a weight group share its existing budget. Optional aspects have a bounded total weight and cannot compensate for missing the central purpose. Freeze the weight policy and any small tuning range on development data.

Use existing IDs/source anchors where possible. Bind changes to source identity; don't use mutable display order as identity. No public raw notices, unrestricted extracted text, or private caches enter ingredient assets.

### 3.3 Researcher passages and evidence provenance

Use the canonical eligible directory, not selected favorable faculty. Preserve active claim IDs/revisions, public evidence text, source links, source-check metadata, and visibility/admission rules. Directory-only, hidden, or ineligible records remain under their existing restrictions. “Rankable” is not synonymous with every named person in the registry.

Keep author-stated interests as interests, and demonstrated work as demonstrated work. Use multiple distinct passages rather than one whole-profile average. Deduplicate identical and clearly repeated claim text, retain all distinct relevant claims within a declared safety bound, and do not rank by publication count, profile length, department, prestige, or popularity.

A profile passage may support one aspect without supporting another. Do not take a method from one unrelated claim and its application context from another to invent a composite capability. An explicitly linked passage set can be used only with retained linkage evidence. Missing context is not a positive compatibility signal.

Prefer descriptors already present in source/claim text. Any extracted operation/object phrase must point to its source span; a generated taxonomy label alone is not evidence. A missing operation descriptor disables that particular method-route feature, not all topic relevance. Do not impose a universal scientific taxonomy or spend on profile-wide generative enrichment as a prerequisite.

### 3.4 Vector and model-space contract

Pin the embedding model, version/snapshot when available, query/document input roles, dimension, normalization, preprocessing, chunk boundaries, and serialization. Equality of vector dimension alone is not compatibility. Reuse existing compatible vectors; do not truncate dimensions, refit PCA, or change query/document modes to make caches appear reusable.

Validate finite values, shapes, norms, source identity, and payload lengths. Reject corrupt/mixed assets instead of silently replacing vectors with zeros. Start with Float32 storage and a deterministic numerical reference; quantify any later compression against ranking parity before using it. Private profile/CV text is not embedded or uploaded by this new public path.

## 4. Numerical relevance without hidden AI work

### 4.1 Declare the gate so it can actually be implemented

For aspect i and passage p, compute a bounded feature vector from the pinned public inputs. Candidate features are contextual aspect–passage cosine, core-purpose similarity, explicitly supported operation similarity, compatible scientific-object/context similarity, specific lexical evidence, missing-descriptor indicators, and generic-only overlap. Start with roughly 6–10 features, not hundreds of hand-maintained rules.

Use two auditable admission routes:

- **Topic route:** contextual aspect relevance and core/context relevance exceed declared development-calibrated floors.
- **Method route:** both source and profile contain supported operation descriptors; method similarity and context compatibility exceed declared floors; the match is not only generic language.

An edge passes if at least one route passes and it violates no machine-supported explicit exclusion. Unknown compatibility cannot count as affirmative method support. Do not infer personal eligibility, facilities, or incompatibility from department or institutional reputation. Contradiction rules must be narrow and source-grounded; cosine cannot prove negation or permission.

Store route, features, supporting passage, and diagnostic reason. This is a fallible relevance filter, not a semantic proof. Hard-negative and positive-transfer development tests set its parameters. No model call or paid remote reranker is allowed to decide the gate at interaction time.

A baseline can combine fixed nonnegative feature weights and bounded monotone similarity transforms. Learn those transforms/floors only from development data. Raw cosine is not a probability. Generic embeddings, near-duplicates, and unequal text lengths are explicit test cases, not assumptions of correctness.

### 4.2 Baseline, regularized, and Bayesian scorers

Use the same gate and features for component comparisons. The event being modeled is: **a knowledgeable evaluator would regard this as a reasonable person to discuss this particular scientific contribution with, based on the available profile**. It is not competence, possession of equipment, willingness, grant success, or verified role completion.

Start with the fixed scorer. Regularized logistic and Bayesian logistic comparisons are optional when suitable development labels and the B1 budget permit:

\[
Y_{ip}\sim\mathrm{Bernoulli}(\sigma(\theta_0+\theta^T x_{ip})),\qquad
\theta\sim\mathcal N(0,\Sigma_0).
\]

Fit transformations and priors/hyperparameters on development data only, using grouped folds. A pooled model is the starting point; no per-faculty models, department-based priors, or automatically added hierarchical layer. A fitted Bayesian model can use deterministic posterior-predictive integration over a checked Laplace approximation. Fixed quadrature or another validated deterministic approximation is suitable; online posterior sampling is not. [R6–R7]

Test fit convergence, finite coefficients/covariance, standardized feature parity, and JS/reference predictions. A fitted covariance that is invalid or a score path with unknown missing-value behavior is a model error, not a reason to return arbitrary defaults. The simpler model remains a valid development-stage choice.

Use posterior means for relevance. Uncertainty may prioritize offline review; it does not earn exploration credit, and sparse profiles are not automatically rejected through an aggressive lower-confidence-bound filter. No Thompson sampling, random user assignment, or automatic retraining from clicks/removals.

For researcher j:

\[
r_{ij}=\max_{p\in P_j}A_{ip}s_{ip},\quad 0\le r_{ij}\le1,
\]

where A is the declared gate and s is the selected bounded scorer. Keep the maximizing evidence passage for explanation. Max aggregation changes calibration and can favor profiles with many chances to match. Test researcher-level calibration, false positives versus passage count, duplicate invariance, and a small top-passage aggregation alternative on development data. Freeze the aggregation before the holdout. More genuinely distinct evidence can legitimately broaden relevance; copying the same evidence must not.

A lower Brier score alone is not proof of better calibration. Compare discrimination, reliability curves with bin counts, log/Brier scores, and sampling assumptions. Until calibration at the actual researcher-recommendation level is supported, call r a relevance score, not a probability. [R8]

## 5. On-demand group selection and alternatives

### 5.1 Weighted coverage remains the primary objective

For an approach a with aspect weights w_i:

\[
F_a(T)=\sum_{i\in a}w_i\max_{j\in T}r_{ij},\qquad F_a(\varnothing)=0.
\]

For a candidate addition j, use \(\Delta(j\mid T)=F_a(T\cup\{j\})-F_a(T)\).

This is weighted facility-location coverage on a scope–researcher graph, not a reward for distance between people. With fixed nonnegative scores and only a cardinality limit it is monotone submodular. Extra feasibility rules and bounded search below do not automatically inherit a textbook approximation guarantee. F is a utility, never a probability of group success or completeness. [R5]

### 5.2 Define feasibility before relative quality

An automatically suggested group must have:

- A meaningful absolute connection to the central scientific purpose, including at least one core-linked researcher. The anchor is scientific relevance, not department.
- At least two admitted researchers and no more than the current four-person limit; fewer than two can still yield individual suggestions but not a fabricated full group.
- A development-calibrated minimum absolute group/core score. Being “best of a bad pool” is insufficient.
- A meaningful final contribution from every automatically added member. Check leave-one-out contribution \(F(T)-F(T\setminus\{j\})\), with the explicit anchor constraint also considered. Do not fill slots with near-zero additions or let later additions make earlier members redundant without reoptimization.
- A single coherent source approach. Distinct alternative branches cannot be complementary roles.

Necessary integration relationships remain visible as limitations. Independent specialists in two measurements do not establish synchronized acquisition. Do not require pairwise faculty similarity or an existing collaboration network: those would suppress reasonable cross-method suggestions. This baseline does not claim to model personal chemistry, availability, or all scientific synergy.

Existing user-selected/explicitly fixed members are constraints, not disposable low-score candidates. Follow current add/remove/option-selection semantics; do not invent a pin control. A manual/unconfirmed member cannot create coverage. Explicit selection of a different group is a user action; automatic recomputation must not silently replace a deliberate selection or reinsert an excluded ID.

### 5.3 Choose team size explicitly

A monotone F tends to improve as people are added. Do not always return four people for that reason.

Find the best feasible candidates for sizes 2, 3, and 4 under the current context. Let F_max be the best score found among them. The default is the smallest feasible size whose score is within a fixed development-chosen tolerance of F_max; initial candidate tolerance: 5%. Apply absolute/core/contribution conditions first. Tie-break by actual score, then stable ID signature.

This is a proposed engineering rule, not a universal optimum. Compare it with a small calibrated size-cost rule on development data only if necessary. Record meaningful counterexamples; do not add a size parameter for every opportunity. Preserve the current view when the user removes someone down to one or zero members.

### 5.4 Search budget, determinism, and all matched people

At the inspected scale, exact scoring of the full eligible directory is the preferred baseline. Use anchored greedy construction with deterministic alternate starts and bounded one-member improvement swaps. Benchmark full-directory seeds before pruning; no hidden top-12 restriction inherited from the old engine. Exact enumeration on small pools supplies an optimization-loss reference. Do not enumerate every four-person combination of the full directory at every click.

The iteration/node budget, tie order, canonical score quantization, and fallback are explicit and versioned. Selection stopping is based on deterministic work units, not which answers happen to finish before a wall-clock timeout. A time safeguard may abort and show the existing error path; it cannot produce a different arbitrary “best so far” group on a slower phone.

Compute dot products in a fixed documented order with a canonical numerical reference. Quantize final comparison scores once, then use stable researcher/approach IDs for a total ordering. Avoid nontransitive epsilon comparators and locale-dependent name ordering as scientific tie-breaks. Test cross-browser/reference parity, near ties, and slightly perturbed scores. Repeatability is not the same as robustness to new evidence; report both.

The full admitted researcher list is separate from the optimizer’s team pool and option list. Never hide someone merely because they are absent from eight returned teams. Replacement/addition order uses marginal contribution to the current selected set while preserving all admitted choices through existing controls. If search pruning is introduced, report its effect against unpruned development tests.

### 5.5 MMR only diversifies already-good alternatives

Create feasible teams first. For each size, approach, and current user-constraint context, retain alternatives within a quality envelope of the best feasible score found for that same context; initial development candidate: at least 95%. Every team also passes the absolute/core/member conditions. A near-best comparison is not made across incompatible source approaches.

Within this pool, optionally apply deterministic MMR:

\[
\mathrm{MMR}(T\mid\mathcal L)=Q(T)-\lambda\max_{S\in\mathcal L}J(T,S),
\]

where J is Jaccard overlap of member IDs, not disciplinary distance, and Q is a declared comparable score. Remove duplicate membership signatures first. Use a small frozen lambda and no random tie-breaking. A “biologist for diversity” cannot enter through MMR because MMR never admits an ineligible researcher or low-quality group. [R9]

Keep the team-size-selected default first on initial display; MMR ranks the remaining alternatives and must not replace that default with a larger group merely for a slightly higher raw score. User-edited selections remain selected even when they are no longer an optimized option.

Return up to eight feasible distinct options; return fewer when warranted. Do not label different staffing combinations as different scientific strategies without source support. Maintain a stable displayed option identity/list for a state so a click by option index resolves the option the user saw. Repeated pure reads must not re-rank options differently.

### 5.6 Limits and honest empty outcomes

Useful partial groups are permitted; this is not “everything covered or no output.” Conversely, no adequate two-person group is a legitimate result even when individual matches exist. Do not lower floors to meet eight options or 150 successful teams.

Track `prepared`, `matched_people_count`, `feasible_team_count`, and evidence-state results separately. A ready source can produce zero teams without being treated as a malformed file. Fixed interface wording must be mapped to truthful existing states; if it cannot express a supported outcome, record the exact presentation conflict for user review rather than lie or redesign.

## 6. View adapter, provenance, and interactive behavior

### 6.1 Separate recommendation score from evidence status

Internally retain both `relevance_score` and `evidence_status`. Every member explanation names the matched aspect and quotes the actual current public passage. A topic relation or an expressed future interest may justify a suggestion but not a statement of demonstrated equipment, clinical access, or fabrication.

Default new approximate links to existing unconfirmed/adjacent states. “Direct evidence” or confirmed method-transfer coverage requires independently supportable evidence for the exact displayed contribution, such as a still-valid previously reviewed link or a narrowly audited source/claim relation; neither score magnitude nor word identity alone suffices. Do not build a second paid capability-certification pipeline to obtain these labels.

Retain validated old evidence where its scope, meaning, and claim revisions really match; do not copy a reviewed flag to a semantically changed aspect. Any deterministic equivalence rule used for evidence status needs development examples and source-based audit. A broad quotation about an opportunity never widens a researcher's expertise.

`complete`, `directEvidence`, `filled`, `gate_state`, selected candidate IDs, and alternative IDs must have mutually consistent meanings. A display may show a reasonable proposed group with unconfirmed aspects. Do not set complete from F, a probability threshold, or the number of selected people. Do not mark every new link direct merely to prevent the UI looking cautious. [R2]

### 6.2 Close the replacement-list trap

The old engine suppresses candidates when role coverage is gap/adjacent and derives replacements only from unfilled roles. For this engine, candidate discovery must be independent of confirmation status. Populate the existing replacement list from admitted scoped matches when a slot is available, including unconfirmed but plausible additions, and retain the corresponding honest label.

All current members, available candidates, and removed-but-explicitly-restorable IDs must resolve to the same registry snapshot. Exclusions affect automatic options but do not prevent the user from deliberately restoring someone through the existing control. Do not automatically re-add removed people after a recomputation or network retry.

The initial recommendation path and subsequent remove/add/variant path must use the same relevance matrix, evidence mapping, and source approach. No stale original member explanation, stale default-team gaps, or taxonomy-only fallback may override the recomputed result.

### 6.3 Preserve existing data and privacy paths

Use stable IDs and backward-compatible saved-state migration. Keep legacy generated-team routing for still-valid scopes outside the new rollout manifest; one coherent scope has one declared engine owner per release. Do not merge half of an old graph with half of a new ingredient result.

Keep manual researchers, ORCID, private CVs, and personal profiles under their current local/admission boundaries. This path does not silently embed them, transmit them, promote them into the public registry, or promise immediate semantic scoring of unprepared private text. Existing handoff continues to work without disclosing private information.

The separate all-member-fit semantics of Team Match remain unchanged. A suggested group's ability to open Team Match does not guarantee that the distinct all-member search will return the same opportunity. No change to general funding ranking, alerts, or source identity is authorized.

## 7. Loading, caches, updates, security, and performance

### 7.1 Versioned ingredient manifest

Use a compact eager availability manifest and bounded lazily loaded ingredient assets. A new explicit schema distinguishes prepared inputs from precomputed legacy graphs. Generated release markers and script/asset references may change only at the recorded nonvisual wiring seam; fixed presentation markup and styles do not. The manifest binds engine/schema versions, source scope descriptors and hashes, registry generation and claim revisions, embedding-space fingerprint, feature/scorer versions, selection rules, all asset hashes/lengths, and per-scope legacy/new routing.

Do not force the new ingredients through a schema that requires an already-filled `members` array. Do not weaken old v1 validation; add version-specific validation and an explicit internal translation. Index readiness means inputs are prepared/current, not that a team is promised. Existing “Build a team” availability, filter/export behavior, and empty outcomes must be tested under that interpretation.

At initial scale, a small eager index plus one lazy shared ingredient bundle is acceptable if it meets measured limits. Further sharding is optional. Do not load the ingredient bundle during ordinary search, score all scopes during initialization, or perform silent background team generation.

### 7.2 Layered cache keys and invalidation

| Layer | Identity and invalidation |
|---|---|
| Public passage vectors | Exact passage/claim revision, embedding-space contract, preprocessing. Display-name changes alone do not re-embed. |
| Scope aspects/vectors | Exact owned scope/source material, aspect extractor/schema, embedding contract. An amendment can affect eligibility separately from semantic vectors. |
| Relevance matrix | Scope/aspect identities, eligible profile-vector identities, feature/scorer versions. |
| Team options/view | Matrix identity, selection rules, coherent approach, selected/excluded/fixed IDs, applicable currentness context. |
| Display metadata | Current compatible public name/source/check metadata; never misstate semantic evidence as freshly revalidated. |

A profile change can alter the best competitors on many scopes. Reuse unchanged vector/score rows, but invalidate cached group selections keyed to the changed registry/matrix. Do not claim unrelated teams are guaranteed identical. A global scorer update can invalidate all matrices while preserving raw vectors.

A cosmetic update must not re-embed everything. A materially changed claim or source must not reuse a stale explanation. Removed/retired claims must not return through a legacy cache. Old negative “no group” results expire by input identity, not permanent exclusion.

Use bounded in-memory LRU caches and immutable HTTP asset caching. Avoid adding persistent private storage or a service worker. Existing local saved IDs stay in the existing versioned storage contract. A cache miss on prepared inputs triggers download/recalculation only, not a provider fallback.

### 7.3 Snapshot consistency and race conditions

Open a panel against one coherent validated package. Never mix latest registry JSON with older vector indices or source recipes. Adopt a new package atomically at the established reload/open boundary; use compatible old evidence only while still eligible. A stale, corrupt, or unavailable recipe should affect its scope, not crash search.

Reapply authoritative currentness on open and subsequent team actions using one decision clock per action. A panel opened before a deadline must not continue producing actionable expired results indefinitely. Reuse the application's existing currentness policy and timezone handling, not a new local date parser.

Discard responses after panel closure, changed scope, generation change, or superseding request. Preserve the existing request-sequence/focus behavior. Rapid child switching, double clicks, back/forward, network retries, and duplicate tabs require explicit tests. Profile changes become visible after a compatible new ingredient publication/load; no claim of instantaneous cross-device freshness is made.

### 7.4 Zero paid interaction calls, verified at the boundary

On a prepared scope, open/options/remove/add/restore/retry must make zero LLM, embedding, or remote-reranker calls. Prove this by blocked-provider test clients and browser network inspection, not just by a cached success test. Test cold asset loading, cache eviction, malformed cache, and failures too. There must be no paid fallback path.

Ordinary static asset requests and unchanged existing analytics are not “model calls.” Record them separately. No new logging of private selections, profile text, or identities is added. Treat embeddings as derived public data; do not assume embeddings of private text would be anonymous.

### 7.5 Security and practical resource limits

Validate manifest hashes, byte lengths, bounds, schemas, vector identities, source URL protocols/hosts, and eligible IDs. Source/profile text is untrusted data, not instructions or executable markup. Existing HTML escaping and source-link safety remain. Do not expose provider credentials, raw private documents, or assessment labels through public bundles.

Stage 1 measures actual asset sizes before promising browser speed. Initial targets to confirm are p95 cached group/replacement recomputation under 200 ms and p95 computation after inputs arrive under 1 s on a declared midrange reference. Report cold download/decode separately. Also target p95 cold click-to-interactive within 5 seconds on a documented reference network (initial proposal: 20 Mbit/s and 150 ms latency); report real-device observations separately from throttled tests. Provisional ingredient ceilings are 8 MiB transferred and 48 MiB additional heap; revise once at Stage 1 with measured justification if inappropriate, not after failures to manufacture a pass.

Use deterministic operation-count caps and a finite source/profile size bound. Avoid uncontrolled DOM/data growth from numerous alternatives. Up to eight options must work with the unchanged renderer at the existing supported widths. Measure ordinary-search startup impact (expected: no ingredient download or team computation), cold/warm memory, network bytes, and long-task behavior. Device emulation is not physical-device testing.

## 8. Evaluation: useful recommendations without self-deception

### 8.1 Fixed corpus and grouping

Retain the proposed 240 cases: 180 coherent scientific scopes and 60 negative/edge controls, across at least six represented research families where inventory allows. Include genuine no-group scopes, sparse/verbose profiles, method-transfer positives, unrelated outsiders, umbrella parents, sibling leakage, source alternatives, expired entries, and conditional constraints.

Group by parent solicitation, successor/near-duplicate scope, and derivative control origin before splitting. Target 120 development (90 eligible/30 controls) and 120 sealed holdout (90/30), allowing documented deviations rather than breaking groups or inventing independence. Do not count a perturbation and its original as two independent calls. Freeze a separate eligible rollout manifest by source/currentness/representation criteria, not observed recommendation success.

Historical exposed trials belong in development/regression reporting. Preserve the earlier twelve confirmations and document any overlap; do not label familiar examples fresh. Known-source overlap is not the same as new independent evidence. These tests assess unseen calls among the current researcher directory, not guaranteed transfer to a new university or entirely new faculty population.

### 8.2 Model-led offline evaluation and bounded human audit (user amendment E1)

Use deterministic tests for objective identities, currentness, ownership, duplicate membership, source-span integrity, numerical behavior, interface contracts and zero-call interactions. Use one fixed rubric-based model judge for most semantic evaluation: individual relevance, applicable method transfer, group coherence, complementarity and explanation faithfulness. Judge whether a collaborator is worth a scientific conversation; never certify facilities, qualifications, willingness or proposal success. Labels are strong / plausible / unrelated / insufficient-information, with ties and unresolved cases retained.

Run judging in an evaluation context separate from implementation and recommendation generation. Supply original bounded call evidence and relevant original public profile passages, not just generated aspects or persuasive explanations. Audit explanations separately. Hide algorithm identities, numerical scores, expected winners and prior decisions; keep substantive evidence and formatting comparable. Use reproducibly balanced ordering and a predeclared small order-swap audit. Conflicts remain unresolved, not rerun until favorable. Prefer an already available different model family from any aspect generator when practical and budgeted; no new provider is mandatory and another model does not guarantee independence.

Marc Porosoff is the sole confirmed human reviewer. Plan at most 40 compact requested items across the entire experiment: up to 20 development rubric/judge checks and up to 20 separate final-audit items after the finalist and judge protocol are frozen. Include individual and complete-team comparisons; no item may hide dozens of subjudgments. Development includes representative, borderline, transfer and unrelated controls. Preselect the final audit without favorable judge scores. Show original source/profile evidence first; hide the judge verdict until Marc records his assessment. Allow unable-to-assess; count every requested item including skips against the cap, with no automatic replacement or extra rounds. Additional human review needs explicit approval. Do not assume a second reviewer or require hundreds of manual labels.

Distinguish human judgments, model judgments and deterministic tests. Model-generated development labels may support optional regularized/Bayesian fitting, explicitly as potentially noisy machine labels, not expert ground truth. Agreement with the training judge does not establish calibrated human preferences. Retain representative sampling/inclusion probabilities or a separate calibration subset, and report systematic errors, disagreements, missing information, empty outputs, denominators and clustered uncertainty. Keep existing targets visible and identify model-estimated versus actually human-observed metrics. The human audit is limited product evidence, not multi-expert validation across all fields.

Use one primary judge, cached exact judgments, deduplicated evaluation items with retained occurrence counts, and a bounded request/token/dollar ceiling approved separately. If judging remains unreliable, report the failure; do not expand providers, human labeling or qualification loops. Safe simple-baseline development can continue with usefulness claims limited to actual evidence. Independently assess source coherence and directory feasibility before judging algorithm output; unclear feasibility remains explicit. Detailed finite item plans, human allocation, prompt/schema, bias controls and trusted-route limitations are in `evaluation-protocol.md` and `annotation-packet.md`.

### 8.3 Development comparison and frozen model choice

Compare A and B on identical snapshots; C and D remain optional under B1:

A. Whole-call embedding relevance with top-k people at matched size.
B. Aspect-level gate plus weighted coverage and deterministic alternatives.
C. B with a regularized logistic scorer over identical features.
D. B with Bayesian logistic scoring over identical features.

MMR/no-MMR is a paired ablation, not another model sweep. Use a small predeclared parameter grid. All preprocessing scalers, thresholds, weight choices, passage aggregation, and model selection use grouped development folds only. Do not fit on all data before splitting. [R7]

Freeze the judge rubric and protocol, candidate selection rule, and primary finalist before final evaluation. Do not tune against the sealed holdout or final human audit. At the end of Stage 2, nominate one primary finalist and at most one simpler fallback under a fixed selection rule. Lock their code, scoring parameters, aspects/preprocessing version, test protocol, and release criteria before inspecting holdout outputs. Do not inspect a holdout leaderboard and then announce whichever arm won as independently confirmed.

Stage 3 evaluates the frozen primary and comparison baseline; a predeclared fallback may also be assessed transparently. A failed primary is recorded as failed. Any use of the fallback is an explicit user-reviewed deployment decision, not erased selection history or a tuned new candidate.

### 8.4 Holdout measurement and uncertainty

For held-out eligible scopes, judge top-five people when available, the primary group, and two alternatives. Audit a stratified sample of further options and post-removal/addition results. Deduplicate repeated judgments of the same aspect/person/evidence while preserving occurrences for per-scope outcomes.

Report model-estimated and actually human-observed metrics separately. Report macro per-scope and member-level metrics, actual list lengths, individual yield, group yield, no-group cases, reasonable-transfer and unrelated-outsider rates, and research-area slices. Bootstrap or otherwise calculate paired uncertainty clustered by parent/near-duplicate group—not by hundreds of correlated team variants. Small subgroups have wide uncertainty; do not claim broad generality from a few cases.

If calibrated predictions are claimed, identify calibration to the fixed model judge versus limited human observations and obtain a representative held-out aspect–researcher sample; top-ranked recommendations alone do not validate full-range probabilities. Match sampling and the predicted event, evaluate after researcher aggregation, and report reliability counts along with proper scores. Do not display numerical probability in the frozen UI.

### 8.5 Proposed release targets, frozen at Stage 1

These are product targets and engineering choices, not measured achievements or literature constants. Under E1, semantic target estimates are primarily model-judged; report the capped human audit separately and never label those estimates human-validated by implication. Stage 1 may revise them once before tuning/holdout, with reasons and user review.

| Dimension | Acceptance and required context |
|---|---|
| Top recommendations | Mean reasonable-or-better precision among available top-five suggestions >=80%. Report short lists, insufficient-information labels, and empty lists; do not improve this by returning almost nothing. |
| Clearly unrelated automatic members | <=5% of audited automatic member occurrences; report clustered uncertainty and transfer/control slices. |
| Useful groups | Primary group judged worth discussion on >=80% of independently feasible scopes; group-output yield on >=85% of those scopes. Also report the unconditional full eligible-scope denominator and uncertain-feasibility count. |
| Complementarity | Improvement over whole-call top-k at matched size without a worse unrelated-member rate. Report paired intervals and effect sizes. If the improvement is inconclusive, say so; do not force adoption of added complexity. |
| Alternatives | Every option passes absolute/core/member conditions and its declared envelope. Distinct membership, stable ordering, no padded slots, no invented claim of different scientific strategy. |
| Calibration | A Bayesian model is not promoted merely for being Bayesian. It must justify added complexity on development evidence and avoid material held-out harm. Brier loss alone is insufficient calibration proof. |
| Invariants | Zero demonstrated identity/privacy/provenance/explicit-scope-exclusion/fabricated-source failures in release tests; zero paid prepared-scope interaction requests. |
| Interface | Presentation freeze and actual reachability/add/remove/child/handoff contracts pass. Exact mock-output parity plus intentional content-change checks. |
| Determinism/performance | Repeated canonical results on fixed supported inputs; declared resource and timing targets measured; no stochastic exploration or timeout-selected groups. |

Threshold point estimates and uncertainty must both be shown. This is a bounded recommendation release, not a statistical proof of future correctness. Do not move a target after seeing the held-out result. If a consequential repair consumes the holdout, preserve the failure and propose a bounded new confirmation at the stage boundary; never redraw until it passes.

### 8.6 Controlled-change and adversarial tests

Require tests for exact duplicates, long versus short profiles, generic words, new unrelated passages, taxonomy/name/department changes, negation, absent operation descriptors, source-span truncation, aspect splitting/reordering, broad/sibling sources, and instruction-like source text.

Delete a supporting claim: its evidence attribution disappears. Delete a selected member: the relevant aspects become less represented and replacements are re-ranked. Add a valid method-transfer example: it remains eligible without asserting special facilities. Replace with an unrelated person: no artificial coverage. Make a profile newly ineligible: it cannot return through cached options. Preserve user exclusions across refreshes of the same state.

Use exact small-pool optimization references and differential JS/offline tests. Test no two-person group, one/zero selected members, all slots full, no additional candidates, fewer than eight options, and many equally good options. Interpret semantic perturbation robustness empirically; do not promise every paraphrase produces identical embeddings.

## 12. Final definition of done

The selected engine is evaluated against a simple baseline with honest uncertainty; uses fixed, relevant scientific aspects and public profile evidence; calculates suggestions/groups on demand; preserves useful cross-domain methods without novelty-for-novelty's-sake; honors all current interface and state contracts; and makes zero paid calls during prepared-scope interactions, including error paths.

The approved 150-scope inventory is live where real source currentness supports it, with parent/child counts reported honestly, valid legacy coverage retained, exact release/test/rollback evidence, and no disguised reactivation of failed Sonnet qualification. Bayesian inference and MMR appear only if justified. Fewer than eight options or no adequate group are legitimate recorded outcomes—not reasons to lower the scientific relevance floor or hide candidates.

No global scientific perfection, complete catalog backfill, model switch, universal capability proof, or guarantee of actual collaboration is required.

## Implementation review before each stage ends

Perform one bounded consistency audit of the changed subsystem, not another broad feature search.
