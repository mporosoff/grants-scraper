# GitHub Pages hosting and data boundary

## Decision

`mporosoff/grants-scraper` is the source of truth, and GitHub Pages is the
canonical application:

https://mporosoff.github.io/grants-scraper/

The application is intentionally public and browser-only. Faculty open the URL
and do not install Python, create an application account, or upload faculty or
opportunity files.

## Architecture

```text
Scheduled GitHub Actions
        |
        +--> fetch and normalize public Grants.gov opportunities
        |
        v
GitHub Pages application and public opportunity asset
        |
        +--> selected AI provider, called directly by the browser
        |
        +--> browser localStorage for the user's local state
```

The scheduled opportunity feed is planned work. The current page uses a bundled
calibration set.

## Public repository and site

The following may be public:

- application source code;
- project documentation and tests;
- normalized federal funding opportunity records;
- official source links;
- generated public opportunity assets; and
- automation logs that contain no secrets or faculty information.

The repository must not contain:

- API keys or provider credentials;
- private faculty research descriptions;
- browser-saved searches or result snapshots;
- exported faculty result files;
- unpublished research information; or
- unnecessary bulk raw API responses and document collections.

## Browser-local information

The application stores the selected provider, API key, research text, saved
searches, result snapshots, and cached embeddings in browser `localStorage`.
This data is specific to the browser profile and is not synchronized or backed
up by the application.

Local storage is not a secure credential vault. Users should use scoped keys
with spending limits and clear the key before leaving a shared device. When
matching runs, research and opportunity text are sent directly to the selected
AI provider under that provider's terms.

## Opportunity refresh

The intended production feed is generated by a scheduled GitHub Action:

1. Query public Grants.gov endpoints.
2. Normalize and validate current opportunities.
3. Fail visibly when record counts or required fields are implausible.
4. Build a JavaScript data asset for the browser application.
5. Deploy the tested static site to GitHub Pages.

Faculty do not run the pipeline and do not manage JSON files. Large raw API
responses should not be committed to the main branch.

## Deployment checks

GitHub Actions should continue to run:

- Python normalizer tests;
- static GitHub Pages entry-point tests;
- checks that no key is embedded in the application; and
- validation of the generated public opportunity feed.

The project should display a visible last-updated timestamp and report a failed
or stale refresh instead of silently serving old data.

## Deliberate limitations

A pure GitHub Pages application does not provide:

- private access controls;
- a central faculty database;
- cross-device saved-search synchronization;
- shared departmental feedback;
- server-side API-key management;
- automatic personalized email digests; or
- administrative review workflows.

Those capabilities require a server or third-party service and are deferred
unless the static pilot demonstrates that they are worth the added complexity.
